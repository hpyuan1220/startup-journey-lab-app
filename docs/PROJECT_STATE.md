## 安全修正紀錄

- 2026-09-17： 檢視表原本繞過 RLS，帶公開 anon key 可讀到全班回饋與學號。
  成因：Postgres 檢視表預設以擁有者權限執行，且 Supabase 預設將 public schema 新物件 SELECT 授予 anon。
  修正：（security_invoker = true + revoke from anon）。
  修正後以 anon key 查詢回傳 401 permission denied。
  教訓：**每次新增 view 都要單獨驗證 anon 權限，底層資料表有 RLS 不代表 view 安全。**

#### 教師登入不再殘留在瀏覽器

實走時發現：一開啟網頁就看得到前一個人的教師登入狀態與整份班級名單。
原因是教師 session 存在 localStorage 且帶 refresh_token 自動續期 —— 等於永久有效。
老師在教室電腦登入後沒登出，下一個開網頁的人就看得到全班姓名與學號。

三道處理：

1. **改存 sessionStorage。** 關掉分頁或瀏覽器即失效；sessionStorage 是分頁層級的，
   另開一個分頁也看不到（實測確認）。統一經過 `teacherStore`，四個檔案都改

#### 修改區從五顆按鈕減到一到兩顆

「把建議改成可編輯草稿」那一區原本同時顯示五顆按鈕，而且分屬兩層：

#### Week 1 重複提交：擋掉無意義的重送，並講清楚第幾版

原本 `$('week1-form').onsubmit` 直接 `save('submitted')`，**沒有任何已提交的檢查**。
學生回來按「正式提交」就再送一次，訊息還和第一次一模一樣（「已正式提交，老師現在可以查看。」），
他不知道這是第幾版、也不知道內容到底有沒有變。不確定有沒有成功就多按幾次，
每一次都會在 `learning_versions` 留下一個內容相同的版本。

資料本身不會掉：`week1_version` 與 `week1_snapshot` 兩個觸發器早就存在，
每次更新 version+1 並快照整份內容，而且 `if old.submitted_at is not null then new.submitted_at=old.submitted_at`
保護了第一次提交的時間。所以「清除內容」那句「原版本會保留」是真的。

三項改動（純前端，觸發器本來就在做事）：

1. **內容沒變就不重送。** `snapshotOf()` 比對十二個欄位，一樣就顯示
   「內容和上次提交的完全相同，不需要重送。」並且**不發出請求**（測試釘住這點）。
2. **有變就講第幾版。**「已更新提交，這是第 N 版。老師會看到最新版本，先前版本也保留著。」
3. **回來時就標明狀態。** 新增 `#submitted-state` 區塊，載入已提交的卡片時顯示
   「已於 9月24日 提交（第 2 版）。可以直接修改後重新提交，先前版本會保留。」
   學生一回來就知道自己在什麼狀態，不用靠按按鈕試探。

89 項測試通過（新增 3 項）。瀏覽器實測：狀態列文字正確、未改動時發出 0 個請求、

#### 教師回饋的兩個缺陷（同日補）

檢查「送出給學生的內容去了哪裡」時發現兩個問題，都是當天新寫的程式造成的。

**一、PATCH 條件漏了班級。** `teacher-note.js` 用
`week1_submissions?student_id=eq.<學號>` 更新，但資料表唯一鍵是
`unique(class_id, student_id)` —— 同一個學號若出現在兩個班，兩邊的 teacher_note 都會被寫入。

**二、老師留言會把學生的版本號往上加。** `week1_version` 觸發器對任何 update 都生效，

`bump_learning_version()` 改為先比較「移除 teacher_note / needs_follow_up / review_status /

`snapshot_learning()` 在 version 沒變時直接 return，不留快照。
第一次提交時間的保護維持不變。**這一份要在 Supabase SQL Editor 執行才會生效。**

#### 預覽會把「沒有差異」的欄位當成待決定的選項

#### A1 已提交的卡可以被清空

可達路徑只要兩次點擊：已提交的學生按「儲存草稿」→ 再按「清除內容」。

- 前端「清除內容」的守門是 `if(savedStatus==='submitted')`，用的是**前端狀態**，
